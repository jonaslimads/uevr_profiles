# SWGRServerPerf-v2: Potato resolution, hot render thread

## Outcome

The user tested the v2 portable injector with Virtual Desktop Potato and still observed 28–30 FPS. Logs confirm 1344 × 1344 per eye, native stereo, synchronization mode 2 (Very Late), and the v2 commit `c13486a8b280ffa59c1d2edb10ee6f582a1632fe`. The earlier user-reported slow session had roughly 35 ms in Virtual Desktop Game and Synchronous Spacewarp disabled. Current overlay values and refresh settings were not independently captured.

The strongest measured bottleneck candidate is CPU work on `RenderThread 0`. Its CPU usage remains close to one logical processor's capacity while device-wide GPU utilization is much lower than the earlier Godlike capture. The measured OpenXR wait, UEVR post-present mutex wait, copies and mirror are small. These measurements support investigating render-thread CPU work before changing frame synchronization or removing locks. They do not identify the expensive functions or prove that injected hooks contribute no CPU cost elsewhere.

## Diagnostic activation

Two startup configuration-load lines report `reset_defaults=false raw=<missing> profile=false launch=true effective=true hitch=false`. The launch override successfully enabled actual OpenXR, D3D12, fence, engine-hook and post-present summaries despite the missing profile option. The original profile reset cause is still unresolved. Hitch snapshots were not enabled.

Injection began at 15:18:12 local time (UTC-03:00), after process 17052 started at 15:17:09. The collector had started at 15:15:58 and captured startup as well as gameplay. The user did not mark the exact race start; the window below is a selected observation interval, not a verified exclusively racing segment.

## Rendering and shutdown evidence

Auto-mono telemetry reports activation at 15:18:51.933 and stereo restoration at 15:19:01.263. This supports that the detector remained operational; it is not a complete user-validated visual regression test. Final scene-capture recreation began at 15:20:52, followed by shutdown pointer-resolution errors. Those events are excluded from the observation window and are not used to explain sustained FPS.

## Next investigation

Capture sampled CPU call stacks for `RenderThread 0` with the same scene/settings, then attribute CPU samples to the engine, UEVR hooks and dependencies. Windows Performance Recorder is present and lists a CPU profile; recording permissions and analysis tooling have not been validated. Engine functions may lack public symbols, but module and address attribution plus the matching UEVR PDB can still distinguish injected work. Preserve the measured baseline and change only the identified expensive path. No concurrency, affinity or rendering optimization is justified solely by aggregate CPU usage.
